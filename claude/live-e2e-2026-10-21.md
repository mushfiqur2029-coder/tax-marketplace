## Test harness

Chrome extension drove the browser. Two helper scripts (throwaway,
removed after the run) seeded the test data outside the UI:

- `scripts/_seed_live_test.mjs` ,  created a disposable client user
  (`ritzbd.com+livetest20261021@gmail.com`) and an approved disposable
  accountant (`ritzbd.com+livetest20261021acc@gmail.com`) via
  `supabase.auth.admin.createUser` + an upsert into
  `accountant_profiles` with `approval_status='approved'`, then minted
  magic-link URLs for both.
- `scripts/_livetest_stamp_payment.mjs` ,  simulated Stripe's success
  webhook by writing the exact fields `route.ts:634-661` writes
  (`stripe_payment_status='succeeded'`, `status='submitted'`,
  `submitted_at`, `stripe_payment_id`, `stripe_checkout_session_id`),
  plus the engagement-sign stamps (`engagement_signed_at`,
  `engagement_pdf_path`, `signature_image_path`) that `signAction`
  would have set on a real sign.

Browser session was established by extracting the access + refresh
tokens from the magic-link redirect's hash fragment, posting them to
`/auth/v1/user` to resolve the User object, building the
`@supabase/ssr` session payload, base64-encoding, and writing the
`sb-{project-ref}-auth-token` cookie on `apisterlingledger.co.uk`
directly. No sign-in form touched.

A one-cookie-per-origin limitation surfaced: switching between the
client and accountant session on the same tab group overwrites the
cookie because they share the same cookie name and domain. Not a
product bug; browsers work this way. Workaround was to re-mint and
re-write when switching identity.

## Bugs found + fixed

### Bug 1, empty accountant queue for PCH cases

Commit **`de3622a`**: *Fix empty accountant queue for PCH cases: RLS
blocked the submit-ready filter.*

The queue-list page reads `pch_cases.engine_snapshot_at` to decide
whether a PCH case is submit-ready (and should be shown). That read
used the session-authenticated supabase client. The
`pch_cases_select` RLS policy from migration 0080 grants a user
SELECT only when they are the ASSIGNED accountant or the client.
queue accountants are by definition neither, so the read came back
empty for every queued PCH id. The in-memory filter then dropped
every queued PCH case from view (silent empty queue, no error).

Fix: scope-limited RLS bypass. The one-and-only read in that block
is for `tax_year` + presence of `engine_snapshot_at`, both derived
flags, so swapping that read to the service-role admin client is
tight.

Caught because the queue was observably empty immediately after a
successful submit-for-review, with the DB clearly showing a
queue-ready case.

### Bug 2 ,  "Take this case" rejects legitimate takes

Commit **`2aeb242`**: *Fix 'not ready to take' false-rejection on
PCH queue cases.*

Exact same RLS wall, this time inside `takeCaseAction`. The pre-
flight gate reads `pch_cases.engine_snapshot_at` to check that the
client has submitted, again via the session client, again blocked
by `pch_cases_select`, so `head?.engine_snapshot_at` was always
undefined and the gate rejected every legitimate take with "Not
ready to take yet. The client hasn't submitted their intake for
review." The accountant case page even surfaced "Intake: Submitted
for review (engine snapshot ready)" on the same card.

Fix: same scoped RLS bypass. Admin client reads the two derived
flags; the actual `UPDATE cases` still runs on the session client so
RLS enforces the race-safe queue preconditions on the atomic flip.

Caught the moment the queue tab started showing the case and I
clicked Take. The pair was tightly coupled; the first fix just
pushed the failure one step later.

## Non-bug observations worth flagging

### Trigger drift between prod and tracked migrations

The `notify_case_change` trigger function running on prod differs
from `supabase/migrations/0042_notification_text_company_name.sql`.
Prod's version suppresses the `new_queue_case` fanout at payment
time for PCH cases (correctly, the queue is gated on
submit-for-review, not payment), and a separate trigger on
`pch_cases` fires the queue fanout when `engine_snapshot_at` lands.
Neither change is in any tracked migration. A `supabase db reset`
or a fresh environment set up from the migrations folder alone will
replay the old behavior (fanout at payment, nothing at submit) and
the queue-timing fix silently regresses.

Evidence from the test case's notifications table:

| time | type | recipient | source |
|---|---|---|---|
| 11:47 | `case_created` | admin | `cases` INSERT trigger |
| 11:51 | `case_status_change` × 2 | client + admin | `cases` UPDATE: `notify_case_change` fired (status flip to submitted) |
| 11:51 | *no `new_queue_case`* | ,  | **expected if tracked migration was authoritative; actual = suppressed** |
| 11:57 | `new_queue_case` × 3 | all approved accountants | `pch_cases.engine_snapshot_at` flip, fired by an untracked trigger |

Not fixed in this session (it's an observed drift, not a user-
visible bug). Recommended follow-up: write a migration that pulls
the live trigger body into the repo so the behavior is codified. To
do that cleanly I need either direct Postgres access
(`DATABASE_URL`), the Supabase management API token, or a one-off
`CREATE FUNCTION get_fn_src` RPC to read `pg_get_functiondef()`.
None were available in this session.

### "Onboarding in progress" badge misapplied to PCH queue cards

Queue cards for PCH cases render *ONBOARDING IN PROGRESS · CLIENT
MAY NEED HELP* above the status chip. That badge is for the LC
tier's onboarding checklist; PCH has an "intake" (different noun,
different schema), and the queue gating now already requires the
client to have submitted that intake before the card appears at all.
The badge is factually wrong on every PCH queue card. Minor copy
bug; left unfixed in this session.

### Submit-time income aggregation collapses platforms

The 15-row fixture CSV had both `UBER BV PAYMENT` and `BOLT
OPERATIONS PAYOUT` transactions. The bank ingest aggregated them
into a single `pch_income_lines` row labelled "Primary platform
(bank-detected)". Whether per-platform separation is intended at
ingest time or whether this is a design choice is a product call.
Flagged, not fixed.

### Bank-clarify chat not exercised

All 15 fixture transactions came back with
`category_confidence='high'`. The clarify chat is only invoked for
medium / low confidence rows, so the UI path couldn't be exercised
this run. Recommend seeding one or two deliberately ambiguous
descriptions (e.g. a bare "PAYMENT RECEIVED" with no payer) in the
next fixture to cover this path.
